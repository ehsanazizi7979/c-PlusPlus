00 The chapter in one minute

Chapter 1 is not about threads yet — it prepares the vocabulary and the C++ idioms that the following chapters need. It moves from how an OS runs programs, through the C++ program structure and the OOP toolchain, to Windows event handling and a reusable linked-list abstraction.

01 / EXECUTION

Processes vs. threads

A process owns an address space; a thread is the unit of execution inside it, with its own program counter, registers and stack. Fast switching creates pseudoparallelism on one CPU.

02 / RESPONSIVENESS

Never block the UI thread

Waiting for input or doing long work on the only thread freezes the application. Move the waiting work to another thread and let the UI thread keep painting.

03 / STRUCTURE

#include, main, namespaces

Headers declare what you use, main/wmain/_tmain is the entry point, and namespaces such as std avoid name collisions.

04 / OOP

Model the problem, not the machine

Turning raw parameters into struct SComplex and then class CComplex makes client code read like algebra: c = c1 + c2.

05 / EVENTS

Windows is event-driven

WinMain registers a window class, creates a window, pumps GetMessage/DispatchMessage, and WndProc reacts to messages.

06 / REUSE

Design the base class well

A carefully designed CList<T> makes CQueue (FIFO) and CStack (LIFO) almost trivial specializations.

Big picture: every later recipe in the book — threads, synchronization, message passing, concurrency patterns — assumes these basics: how a program starts, how objects communicate, and how a Windows application reacts to events instead of running one linear script.

02 Detailed summary

Introduction — processes, threads and pseudoparallelism

  • An operating system's central abstraction is the process: an executing program with its own address space and (traditionally) one primary/main thread.
  • On a single CPU, the OS switches between processes every few milliseconds. That illusion of simultaneity is pseudoparallelism, as opposed to real parallelism on multiprocessor hardware.
  • A thread keeps a program counter (the next instruction), registers (current variable values) and a stack (function calls and parameters). Threads run in the process context but cooperate: they share processor time, memory and variables. The book contrasts the "greedy" process with more "friendly" threads.
  • Windows gives each process a large virtual address space — a quasi-parallel context even where physical memory is smaller.

Recipe 1 — Creating a C++ project

  • Use Visual Studio: Templates → Visual C++ → Win32 → Win32 console application; name the project, accept the wizard defaults, and edit TestProject.cpp.
  • The generated stdafx.h/.cpp form the precompiled header used by IntelliSense's Translation Unit model; targetver.h controls the Windows target version.
  • Execution starts at main; Unicode builds use wmain, and _tmain expands to whichever one _UNICODE selects.
  • For a 64-bit build: add the x64 platform in Configuration Manager and replace WIN32 with _WIN64 under Preprocessor definitions.
  • Runtime library matters when deploying: /MTd (Debug) or /MT (Release) avoids a dependency on the C++ redistributable; DLL-linked defaults are fine on the development machine.

Recipe 2 — Program structure, execution flow and runtime objects

  • Four paradigms are named: imperative, declarative, functional/structural and object-oriented; C++ supports both structural and OOP styles.
  • The book adopts Hungarian notation: CTest for a class, iCount for an int, dValue for a double — the prefix tells you the type at a glance.
  • #include <header> searches configured include paths; #include "header" searches the project folder first. using namespace std; lets us write cout instead of std::cout.
  • Four console entry-point shapes are shown; the recommended one is int _tmain(int argc, TCHAR* argv[]). argc counts arguments, argv[0] is the program name, and returning 0 conventionally signals success.
  • A single-threaded program runs line by line. Waiting for user input or updating a progress bar in the same loop stalls painting; the fix is a separate thread that signals the UI thread when work is done.
  • A static library (.lib) is linked into the executable at compile time; a dynamic library (.dll) is linked at runtime and can be shared by many programs (e.g. GUI APIs in User32.dll).
Why this matters for multithreading: the chapter's first concrete motivation for threads is responsiveness — long calculations, user input and remote responses must not freeze the UI thread.

Recipes 3 & 4 — From structural code to objects

  • Structural version: ComplexAdd takes six double parameters — real/imaginary parts of two operands plus two reference outputs. It works, but the call site is hard to read.
  • Struct version: struct SComplex { double dReal, dImg; } reduces the signature to two operands and a returned struct. Naming the abstraction immediately improves the code.
  • OOP version: CComplex hides its data, offers two constructors (random or explicit), and overloads operator+ and operator<< as friend functions so they can reach private members. Client code becomes CComplex c = c1 + c2; cout << c;.
  • Overloading can be a member that changes the calling object, or an external friend function when the operator naturally takes two equal operands.

Recipe 5 — Inheritance, overloading and overriding

  • CPerson (age, name, virtual WhoAmI()) is the base; CWorker : public CPerson adds employment status, CStudent : public CPerson adds an ID card. "B is a kind of A" is the modelling rule.
  • Constructors run base first, derived second; destructors run in the opposite order. The derived constructor forwards shared data with an initializer list: CWorker(...) : CPerson(iAge, sName) { ... }.
  • Objects with virtual functions carry a vtable pointer at offset +0, followed by inherited fields and the derived fields — illustrated in the book's layout diagrams (see Figures).
  • Overloading gives an operator a new meaning for a user-defined type (the book mentions matrix addition); overriding replaces a base method's implementation in a derived class. WhoAmI() prints "I am a person / worker / student" depending on the actual object type.

Recipe 6 — Polymorphism

  • CFigure is an abstract class: three pure virtual functions (FigureType(), Circumference(), Area()) end in = 0, plus a virtual destructor. You cannot instantiate it, but you can point to its derived types.
  • CTriangle (Heron's formula), CSquare and CCircle implement the three methods with their own geometry.
  • The demo stores CFigure* figures[3], fills it with derived objects, and calls each method through the base pointer. Dynamic binding resolves the real object type at runtime and calls the right override — possible only for virtual methods accessed via a pointer or reference.
  • Contrast: cPerson.WhoAmI() is bound at compile time because the static type is known; figures[i]->Area() is bound at runtime.

Recipe 7 — Event handlers and the Windows message loop

  • Event handling lets a program react to user actions (button presses, keystrokes, timers). Windows calls a window procedure — conventionally WndProc — whenever a message arrives for that window.
  • WinMain(hThis, hPrev, szCmdLine, iCmdShow) replaces console main; WINAPI is the stdcall convention. hPrev is always NULL in modern Windows.
  • Populate WNDCLASSEX (size, style, background brush, cursor/icon, instance, class name, lpfnWndProc), call RegisterClassEx, then CreateWindow, ShowWindow and UpdateWindow.
  • The message loop GetMessage → TranslateMessage → DispatchMessage keeps the app alive but responsive; WM_CLOSE triggers PostQuitMessage(0), and unhandled messages go to DefWindowProc.
  • On shutdown: DestroyWindow, UnregisterClass, return msg.wParam.
Connection to threads: this queue-and-handler architecture is the Windows answer to "don't block the main flow". Later chapters reuse the same event-handling pattern while moving work onto worker threads.

Recipe 8 — Generic linked list, queue and stack

  • CNode<T> holds a T* and a next pointer; CList<T> manages head and dwCount. It stores pointers to external objects, never copies, which also permits polymorphic elements.
  • Operations: Append (tail, recursive), Insert (head), Remove, GetFirst, GetLast, GetNext, Count, Head, and a predicate-based Find.
  • Copy constructor and operator= are declared protected: that prevents accidental shallow copying by users while still allowing derived classes to have their own copy semantics. Declaring them also stops the compiler from generating public defaults.
  • CQueue<T> = Append at tail + GetFirst/Remove at head → FIFO. CStack<T> = Insert at head + GetFirst/Remove → LIFO.
  • Find accepts a function pointer, so the same list works with a static class method (CStudent::GetStudentId) or a plain predicate for primitive int* values.
  • The book's demo fills a queue and a stack with 10 values, drains them, and shows 0 1 2 … 9 for the queue versus 9.0 8.0 … 0.0 for the stack.
Practical caveat: the sample calls delete on the queue/stack wrappers but not on the individually allocated elements — a real production version would need clear ownership rules or smart pointers.

07 Chapter 2 — The Concepts of Process and Thread

Chapter 1 explained the C++ building blocks; chapter 2 supplies the operating-system model underneath them. It answers three questions: what a process is to the OS, how independent processes can cooperate safely, and how threads differ from processes in implementation and scheduling.

PROCESS

A resource container

An instance of an executing program with a virtual address space; the OS represents it with a Process Control Block (PCB).

THREAD

The schedulable unit

Processes do not receive CPU time — their threads do. A thread owns a program counter, registers and a stack.

IPC

Cooperation needs rules

Shared buffers create race conditions; mutual exclusion, critical sections, mutexes and semaphores impose order.

IMPLEMENTATION

User space vs kernel

Threads can be managed by a library the kernel never sees, or by the kernel itself with a thread table and system calls.

09 Chapter 2: detailed summary

Introduction — multitasking is an illusion on one core

  • Modern machines run many hidden processes (mail, antivirus updates) alongside user work. A multitasking OS switches the CPU between them every few milliseconds, so only one process runs at any instant — the user sees parallelism.
  • The OS uses a sequential process model: all runnable software, including the OS, is a set of sequential processes. A process is an instance of an executing program with its own virtual address space and a thread of control; the scheduler allocates CPU time to that thread.
  • On a single-core CPU, four programs share one instruction pointer and take turns. On a multicore CPU, four processes can each have their own control flow and run independently — see Figures 1–3.
  • Traditional systems give each process one thread; threads let several activities share one address space, which makes concurrent programming much easier than coordinating separate address spaces.

Recipe 2 — The process model and the three states

  • Four events create processes: system initialisation, a process-creation system call by a running process, a user request, or initiation of a batch job. Foreground processes interact with users; background processes handle mail, printing and similar services.
  • CreateProcess creates both the process and its primary thread and loads the context. It returns process and thread identifiers in PROCESS_INFORMATION; those IDs are valid until termination and can be used with APIs such as OpenProcess/OpenThread.
  • Because CreateProcess returns before the child is ready, a parent can call WaitForInputIdle before looking for the child's window.
  • ExitProcess is the orderly termination path: attached DLLs are notified. TerminateProcess skips those notifications, and ExitProcess also ends sibling threads without letting them run their termination code.
  • The book's state diagram has three states: Running (using the CPU), Ready (runnable but no CPU yet), and Blocked (cannot run until an external event occurs). Four transitions connect them: wait for input (1), preemption (2), scheduling (3), and input arrival (4). Figures 4 and 5 illustrate the process launch and the state machine.

Recipe 3 — How the OS represents a process

  • The Process Control Block is the kernel's representation of a process. Its fields fall into three groups: process identification data, processor state data, and process control data. Pointers between PCBs form scheduler queues for Ready, Blocked and other states.
  • NtProcessDemo starts Notepad, loads ntdll.dll, resolves NtQueryInformationProcess with GetProcAddress, and reads PROCESS_BASIC_INFORMATION to print UniqueProcessId.
  • The structure also contains PebBaseAddress, a pointer into the child process. Inspecting that memory would require ReadProcessMemory — the demo only reads the ID.
Why the indirect call? NtQueryInformationProcess is an internal Windows routine, so the example defines its own function-pointer typedef instead of calling a documented Win32 wrapper.

Recipe 4 — IPC, race conditions and mutual exclusion

  • Two processes can corrupt shared state. The airline-seat example: two sellers may both sell the last seat. The CD-burner example is more concrete: processes 5 and 6 both read p_free = I6, one is preempted, and both write to slot I6 — the second overwrites the first (Figure 7).
  • When the outcome depends on precisely when entities interleave, that is a race condition. The region of code touching shared data is the critical section.
  • Four requirements for a correct solution: no two processes inside their critical regions at once; no assumptions about CPU speeds or count; a process outside its critical region must not block others; and nobody may wait forever to enter.
  • The IPCDemo/IPCWorker projects put a COMMUNICATIONOBJECT in a named file mapping (window handle, exit flag, sleep timeout) and guard it with a named mutex. Workers call OpenMutex, WaitForSingleObject, MapViewOfFile, paint a rectangle, then ReleaseMutex; the parent starts one red and one blue worker and posts PostQuitMessage on WM_DESTROY.
  • Passing (HANDLE)-1 to CreateFileMapping creates shared memory backed by paging—not a real disk file—and the workers are distinguished by the command-line argument "red" or "blue".

Recipe 5 — Dining philosophers, deadlock and starvation

  • Dijkstra's problem (from Tanenbaum): five philosophers alternate thinking and eating; each needs two forks from a table with five forks. If all take their left fork simultaneously, nobody can get a right fork — deadlock.
  • "Put the fork back if the right one is busy and retry" avoids deadlock but can cause starvation: everyone keeps repeating the same fruitless cycle without progress.
  • A single mutex around fork acquisition is correct but allows only one eater at a time. The book's solution uses a semaphore initialised to PHILOSOPHER_COUNT / 2 (two permits), so up to two non-adjacent philosophers can eat simultaneously. Each philosopher process waits on the semaphore, checks both neighbour flags in shared memory, eats for one second, signals the UI with SendMessage(WM_INVALIDATE), then releases the semaphore.
  • Other classical problems mentioned: sleeping barber and producer–consumer (bounded buffer), the latter revisited in recipe 8.
Original wording preserved: the summary corrects the sense, but the code cards keep the book's own comments and identifiers — including iPhilosopherArray and EATING_TIME.

Recipe 6 — From process image to thread model

  • A process image groups the address space and all resources — code, data, heap, stack, file handles, child-process information, alarms and signal handlers (Figure 10). It is loaded when CreateProcess initialises the process.
  • A thread is the lowest schedulable entity: a process itself never gets CPU time. Threads save register values and a stack with one frame per active function call.
  • Three processes with one thread each and one process with three threads both give three schedulable flows, but only the second case shares an address space (Figures 11–12). This is what "multithreading" means.
  • MultithreadedArraySort fills 200 random values, starts two threads via CreateThread, sorts each 100-element half, waits with WaitForMultipleObjects, then merges the halves — a textbook divide-and-conquer demonstration.
  • CreateThread takes a start address (LPTHREAD_START_ROUTINE), a single LPVOID parameter, flags and an optional thread ID. Pass a struct or class by address when a worker needs more than one value.

Recipe 7 — Thread usage with a database

  • The MySQL C-connector example wraps a connection in a singleton CMySQL with CreateInstance/ReleaseInstance, connect/disconnect, and ReadData/WriteData helpers.
  • Three threads receive QUERYDATA structures (two selects, one update). Their start routine enters a global CRITICAL_SECTION, connects, performs the query, disconnects and leaves — guaranteeing that no thread reads or writes while another is using the connection.
  • The alternative is to let the DBMS coordinate with table locks (lock table ... read/write, unlock tables), with the caveat that lock granularity varies across MySQL engines such as InnoDB and MyISAM.
  • Critical sections are examined in more depth in chapter 3 of the book.

Recipe 8 — Threads implemented in user space

  • In a user-level threads package the kernel knows nothing about the threads: it sees an ordinary single-threaded process. A runtime library manages create/terminate and scheduling, so threads can run even on an OS without native thread support.
  • ConcurrentFileCopy is the producer–consumer case: a read thread fills a memory buffer block by block while a write thread drains it, and a progress bar shows the copied blocks. Both threads use a named mutex around access to the shared byte counts and buffer.
  • The write thread checks dwWriteBytes < dwReadBytes before writing, because scheduling order is unpredictable — the consumer might otherwise try to write data that has not been read yet.
  • Trade-off: user-space thread switches are cheap, but a blocking system call blocks the whole process, since the kernel only sees one thread.

Recipe 9 — Threads implemented in the kernel

  • The kernel is itself a process with many system threads. It keeps a thread table in addition to the process table; blocking calls become system calls, and when a thread blocks the kernel must run another one. Destroyed threads can be recycled.
  • The demo has two projects: a Win32 loader (ThreadApp) that copies TestDriver.sys into the system directory, creates a service and starts/stops it, and a driver (DriverApp) that creates a system thread in DriverEntry.
  • PsCreateSystemThread starts ThreadStart, which prints its thread ID with DbgPrint, signals a KEVENT, and calls PsTerminateSystemThread. The driver waits with KeWaitForSingleObject and closes the handle with ZwClose.
  • Because kernel code can crash the whole machine (BSOD), the example wraps operations in __try/__except and declares variables before statements (C compilation mode). The chapter closes by noting that hybrid user/kernel implementations exist and that process creation from a multithreaded process raises further design questions.

16 Chapter 3: detailed summary

Introduction — the thread lifecycle

  • Three operations matter: a thread is created with CreateThread, terminates when its start routine returns, and can be joined by another flow that must wait for it. Every process starts with at least one thread — the main thread.
  • CreateThread takes security attributes, stack size, a start address, one LPVOID parameter, creation flags and an optional thread ID. Threads may run asynchronously (caller continues) or synchronously (caller blocks until completion).
  • TerminateThread is possible but discouraged: it does not free the stack cleanly, notify attached DLLs or release handles. Normal return sets an exit code, signals the thread object and, if it was the last thread, ends the process.
  • "Joining" describes the dependency: if thread A needs output from thread B, A waits until B completes. This is the basic building block for coordinated work.

Recipe 1 — Processes versus threads

  • A process must load a file from disk and occupies a complete address space with object contexts and file handles — expensive to create, and communication requires IPC because addresses are private. Use processes for daemons, listeners and genuinely isolated work.
  • A thread needs only a start address in the same code segment (or a DLL), starts much faster and can share handles, pointers and objects directly. For smaller concurrent operations, threads are usually the right choice.
  • tmpThread demonstrates the contrast in one program: CreateThread with a local StartAddress, and CreateProcess with a Debug/Release path to tmpProcess.exe, followed by WaitForSingleObject and CloseHandle.
  • Figures 1 and 2 contrast three separate process address spaces with one process containing three threads. The book's rule of thumb: create a thread whenever the program performs an asynchronous operation — one thread per window, one for keyboard input, one for screen updates, one for autosave, and so on.

Recipe 2 — Permissive vs preemptive multitasking

  • In permissive (cooperative) multitasking, applications must voluntarily return control to the system so another process can run. This was used before Windows 2000 and relies on the programmer's good behaviour.
  • In preemptive multitasking, the OS suspends threads itself to distribute processor time. It does not depend on application co-operation, which makes execution simpler and safer. Modern Windows is preemptive.

Recipe 3 — The Windows Thread object

  • The Object Manager creates each thread as an object with attributes and methods. Attributes include client ID, context, dynamic/base priority, processor affinity, execution time, alert status, suspension count, impersonation symbol, termination port and exit status (Figure 3).
  • Methods include create/open/query thread, set information, get/set context, suspend/resume, alert and register termination port; most map directly to Win32 APIs such as SuspendThread.
  • User-mode code cannot inspect object internals directly. It receives an identification code (handle) and passes it to APIs; only the Object Manager changes object state.
  • With a thread handle you can raise or lower priority, pause or resume, terminate, and query the exit code.

Recipe 4 — Basic thread management with CThread

  • CThread is abstract: subclasses implement Run(LPVOID). A static StartAddress receives this and dispatches to the virtual Run, which is how a C-style thread callback becomes a C++ method.
  • Seven bit flags describe state and behaviour: STATE_RUNNING, STATE_READY, STATE_BLOCKED, STATE_ALIVE, STATE_ASYNC, STATE_SYNC and STATE_CONTINUOUS.
  • Create stores the parameter, creates the thread and optionally an event for continuous loops. Join waits on the thread handle; Suspend/Resume manage STATE_BLOCKED; Alert signals the shared event so every continuous thread can exit normally.
  • CLock is a small RAII helper: its constructor creates/opens a named mutex and waits for ownership; its destructor releases and closes the handle. That is why STATE_SYNC needs only a different flag at the call site.
  • The main.cpp demo derives Thread, creates two windows (each with its own message loop) on two threads, then joins both.

Recipes 5 & 6 — Unsynchronised vs synchronised painters

  • AsyncThreads.cpp creates a main window with four child areas and four threads. Each derived Thread::Run gets its child HWND through GetUserData, obtains a device context, draws ten random rectangles with its own brush, releases the DC and sleeps.
  • Threads are created with STATE_ASYNC | STATE_CONTINUOUS: they repaint repeatedly and independently. The thread array is stored on the main window with SetWindowLongPtr(GWLP_USERDATA) so WM_CLOSE can call Alert() once and then Join() each thread.
  • SyncThreads.cpp is intentionally almost identical — only STATE_ASYNC becomes STATE_SYNC. With the single brush now shared, StartAddress wraps Run() in a CLock, so only one painter holds the resource at a time.
  • The chapter's lesson: good up-front object-oriented design means switching behaviour costs one flag, not a rewrite.

Recipe 7 — The Win32 synchronisation toolbox

  • A busy-wait on a global Boolean like bDone works but burns CPU. Windows synchronisation objects put waiting threads into a queue so the dispatcher can wake them only when the signal arrives.
  • Mutex — a narrow gate with one owner. CreateMutex (with optional initial owner and name), OpenMutex, then WaitForSingleObject/ReleaseMutex. Ownership is cooperative: threads must agree to take the mutex before touching the shared resource.
  • Semaphore — a gate with a counter: lInitialCount and lMaximumCount. Ideal for limiting workers to the number of logical cores; ReleaseSemaphore can add more than one permit when needed.
  • Event — a broadcast signal. Manual-reset events wake all waiters until ResetEvent; auto-reset events wake one waiter per SetEvent. PulseEvent briefly signals then resets. CreateEventEx adds flags and an access mask.
  • Critical section — mutex-like but process-private and faster: declare CRITICAL_SECTION cs, call InitializeCriticalSection, Enter/TryEnter, LeaveCriticalSection, and finally DeleteCriticalSection.
  • Mutexes, semaphores and events can be shared across processes by inheritance, DuplicateHandle, or opening a named object. They live until all handles are closed with CloseHandle.

Introduction — messages are events you can program

  • An event-driven system reacts to signals: mouse movement raises X/Y coordinate events, a key press raises a key event. The OS raises thousands of events per millisecond, mostly invisible to the user.
  • At OS level one form of event is a message: a click calls the window procedure for the window under the cursor, passing a message code and event-specific details such as coordinates.
  • A top-level window must implement a handler (WindowProcedure/WndProc). The main thread's window queue can receive messages from other threads; PostThreadMessage is the alternative when there is no UI, but the target thread must own a message queue.

Recipe 1 — Basic Message Passing Interface

  • basic_MPI.cpp registers a window class, creates a main window plus three child controls (two BUTTONs and one STATIC label), and runs the standard GetMessage → TranslateMessage → DispatchMessage loop.
  • Child-control IDs (BUTTON_MSG, BUTTON_CLOSE, LABEL_TEXT) are passed in the hMenu argument of CreateWindow. They must be unique per parent window and are how a child notifies its parent.
  • In WM_COMMAND, the low word of wParam identifies the control: "Show msg" opens a topmost message box; "Close me" posts WM_CLOSE.
  • WM_MOUSEMOVE uses GET_X_LPARAM/GET_Y_LPARAM to extract coordinates and writes them into the label with SetWindowText. WM_DESTROY calls PostQuitMessage; unhandled messages go to DefWindowProc.
  • Messages are easier than specialised synchronisation objects when a worker simply needs to say "I'm done" to the UI thread.

Recipe 2 — A message queue for producer/consumer work

  • Scenario: draw a four-axis plot while several calculation threads produce results faster than the single drawing thread can render them. The solution is a queue between producers and consumer.
  • queue_MPI.cpp defines user messages above WM_USER (1024): WM_PLOTDATA for "result ready" and WM_ENDTASK for "drawing complete". Custom messages leave wParam/lParam to the application — here lParam carries a PLOTDATA*.
  • Four calculation threads enqueue PLOTDATA into a CQueue<PLOTDATA> under a CRITICAL_SECTION, then PostMessage(hWnd, WM_PLOTDATA, 0, (LPARAM)pData). One draw thread waits on a named event, dequeues under the same critical section, sleeps to simulate slower drawing, updates the label and deletes the object.
  • The queue's address can be attached to the window with SetWindowLongPtr(hWnd, GWLP_USERDATA, ...) and recovered with GetWindowLongPtr. Calculation sleep is 1 s versus 2.3 s for drawing, deliberately creating a backlog.
  • PostMessage vs SendMessage: posting returns immediately; sending waits for the callee to process the message. Messages are fetched with GetMessage or PeekMessage.

Recipe 3 — Thread message queues without a window

  • threadMPI.cpp defines T_MESSAGE ("do the task") and T_ENDTASK ("application is closing"). A worker thread that owns no window has no message queue, so it calls PeekMessage(&msg, NULL, WM_USER, WM_USER, PM_NOREMOVE) to force the OS to create one.
  • The main thread creates an event, starts the worker, saves its thread ID in window user data, and waits for the worker to signal that the queue exists before posting anything.
  • A button in WM_COMMAND retrieves the ID with GetWindowLongPtr and calls PostThreadMessage(id, T_MESSAGE, 0, 0). The worker's own GetMessage loop switches on the message: show a message box, or return on T_ENDTASK.
  • On shutdown the main thread posts T_ENDTASK, waits on the thread handle and closes it. The book's analogy is a weather application: one thread reads physical sensors, another waits for and displays the collected data.

Recipe 4 — Named pipes for process communication

  • A pipe is an in-memory object with two ends: the creator is the server, the connector is the client. One writes, the other reads. The example name is \\.\pipe\basicMPI.
  • pipe_server.cpp loops forever: CreateNamedPipe with PIPE_ACCESS_DUPLEX, blocking message mode and unlimited instances; ConnectNamedPipe blocks until a client arrives; each connection is handed to a new thread so the main loop can accept the next client.
  • The worker thread allocates request/reply buffers on the process heap, reads the request with ReadFile, writes a "default answer from server" with WriteFile, then FlushFileBuffers, DisconnectNamedPipe, CloseHandle and frees the buffers.
  • pipe_client.cpp opens the pipe with CreateFile, waits with WaitNamedPipe, sets PIPE_READMODE_MESSAGE via SetNamedPipeHandleState, writes a message and reads the reply in a loop (handling ERROR_MORE_DATA), then closes the handle. CallNamedPipe is a simpler alternative.
  • The chapter closes by encouraging combination of the techniques: message queues, thread queues and pipes each solve a different communication shape.

30 Chapter 5: detailed summary

Pseudoparallelism — why more threads can be slower

  • Splitting a sum of x iterations between two threads does not halve the time on a single core: only one thread executes at any instant, and the OS must schedule both.
  • Eight threads on one core make things worse — extra thread creation, division overhead and waiting on synchronisation all add cost. Threads help when tasks block (input, I/O, remote calls) or when real cores are available.
  • Pseudoparallelism is still valuable: typing in Word while playing music, printing and burning a DVD feels simultaneous because the OS switches among threads very quickly.

Priority — controlling how often a thread runs

  • Priority controls how often a thread gets CPU time; synchronisation controls competition for shared resources and ordering. Interrupts outrank user processes; a thread's base priority comes from its owning process.
  • Code can move a thread's base priority only ±2 levels — a thread cannot be more important than its process. The OS can go further with dynamic priority: keystrokes, mouse clicks and disk data arrival temporarily boost the waiting thread.
  • Dynamic priority decays one step each time the thread receives its CPU time, settling back to base priority. The dispatcher picks the next thread by dynamic priority (Figure 1).
  • basic_priority.cpp keeps the UI thread at least one step above the drawing thread so the window stays responsive. On exit, an event is signalled and WaitForSingleObject joins the worker.
  • Warning: raising many priorities does not make a system faster — the OS then struggles to run its own tasks. Only a few processes (e.g. dwm.exe, taskmgr.exe) run above NORMAL.

The dispatcher object and scheduling

  • The dispatcher scans the ready queue from high to low priority, but not every thread is in that queue. Thread states: Ready, Standby, Running, Waiting, Transition and Terminated.
  • Loading a thread's context means restoring machine registers, kernel stack, environment block and user stack. If part of the context is swapped to disk, the thread sits in Transition until the system gathers it.
  • A thread runs for a quantum. A clock tick counter decreases until zero, then the dispatcher performs a context switch and selects the next thread.

The shared task: solve systems of two equations

  • Four variants use the same shape: a file of six coordinates per line (a1 b1 c1 a2 b2 c2) is loaded into a CQueue<QueueElement>; workers dequeue one system, solve it by Cramer's rule, update a progress bar and print the result.
  • QueueElement carries the six coefficients plus the HWNDs of the progress and result controls. The UI offers Browse and Start buttons, a label, a result area and a progress bar.
  • The design questions come first: how many threads, and what must be protected? The queue's Dequeue is the bottleneck — it must be exclusive.

Recipe 4 — Mutex

  • Query GetSystemInfo and start at most one thread per processor using sysInfo.dwNumberOfProcessors; SetThreadIdealProcessor hints where each should run (not a guarantee).
  • A named mutex protects queue.Dequeue(): one worker at a time takes a task. This is the "narrow gate" pattern applied to a concrete shared object.

Recipe 5 — Semaphore

  • Instead of creating N threads, create a semaphore with initial and maximum count equal to the CPU count. Workers wait on it with WaitForSingleObject(hSemaphore, INFINITE) and release with ReleaseSemaphore(hSemaphore, 1, NULL).
  • Same result, different technique — a reminder that the first correct solution is not the only one.

Recipe 6 — Event

  • The mutex still protects the queue; a named event is added so the user can abort. Each worker checks the event with WaitForSingleObject(hEvent, 10) (10 ms) at the top of its loop and exits if signalled.
  • This makes the application more responsive and shows how exclusive access and signalling usually appear together in multithreaded code.

Recipe 7 — Critical section

  • Critical section behaves like a mutex but is process-private and cheaper to create/manipulate. Since this application lives in one process, CRITICAL_SECTION plus EnterCriticalSection/LeaveCriticalSection is enough.
  • Choose between mutex and critical section by predicting use cases: cross-process sharing requires a mutex; single-process speed favours a critical section.

Recipe 8 — Pipes across process boundaries

  • The final version replaces worker threads with separate ClientProcess instances. Macros in main.h define the pipe, event, mutex and file-mapping names. The parent creates all four objects before the message loop and disposes of them afterwards.
  • A ListenerRoutine thread loops on ConnectNamedPipe, spawning a worker thread per client. The worker reads a request, takes the mutex, dequeues a QueueElement, writes it into shared file mapping (sized sizeof(QueueElement)), releases the mutex, and sends the coordinates through the pipe.
  • The client retries CreateFile with 0.1 s delays (many processes start at once, so ERROR_INVALID_HANDLE is likely), announces its PID with WriteFile, waits for a request like OK12345, then takes the mutex, reads coordinates from the mapping, solves the system and writes the result back.
  • Trade-off: processes are isolated by address space — safer by default — but slower to create and communicate through. Threads share everything, which is fast but demands careful synchronisation.
Chapter's closing advice: these techniques are "ground zero". Understand the process model, IPC and design before attempting complex concurrent systems.

37 Chapter 6: detailed summary

Managed versus unmanaged code — the trade-off

  • Unmanaged code is compiled directly into machine language and runs on the HAL: fast, low-level, and completely under programmer control. All earlier chapters used this approach.
  • Managed code is compiled to MSIL and executed by the CLR. Static type checking, runtime checks and a garbage collector come for free — but execution is slower and you can only do what the framework exposes.
  • The book's rule of thumb: native C++ (even assembly) for a nuclear power plant controller; .NET for a DVD rental UI that must look good and be finished quickly.
  • The syntax mirrors the two worlds: new/*/& allocate and reference unmanaged memory, while gcnew/^/% use the CLR heap, managed handles and managed references. GC reclaims the latter; addresses may move.

How .NET threading works — Task first

  • Thread lives in System::Threading; Task and its helpers live in System::Threading::Tasks. A Task abstracts concurrent work, while the CLR schedules it onto threads from the ThreadPool.
  • Creating a Task adds work to a queue; an available thread takes it. The pool uses work-stealing: simple work runs inline, complex work is split and idle threads on other cores steal sub-tasks, then results are merged.
  • The book recommends Task over a fixed number of Threads: hard-coding thread counts does not scale, can exceed core count and makes the UI unresponsive. (Thread is not available for Windows Store apps; Task is.)
  • The first CLRApplication example computes 25! on a Task while the main thread owns the UI. The worker may not touch the progress bar it did not create — it builds delegates and calls form->BeginInvoke(action) to have the UI thread do it.
  • _tWinMain sets [STAThreadAttribute] for COM-friendly UI, enables visual styles, and calls Application::Run(gcnew MyForm()).

Foreground and background threads

  • Foreground threads keep an application alive as long as they run. Background threads are killed automatically once the last foreground thread ends.
  • Thread objects are foreground by default; Task work runs in the background. Use a foreground Thread when the work must finish even if the user tries to close the window; use Task when closing the app should simply stop it.
  • The same Thread can behave as background with one line: thread->IsBackground = true; before Start().

Blocking, locks and the deadlock illustration

  • Blocking primitives: Thread::Sleep suspends for a time, Thread::Join waits for termination, and Task::Wait waits for completion — all preferable to a busy spin loop.
  • The CLRApplication3 version asks the user "calculate again?" by posting a custom END_TASK window message from the worker, overriding WndProc in the form. It needs User32.lib, which is implicit in native projects but must be added explicitly in CLR.
  • While waiting for the answer, the worker sleeps one second per iteration. The chapter calls this primitive and shows the .NET alternatives next.
  • CLRApplication4 adds a small RAII Lock class: its constructor calls Monitor::Enter(lockObject), its destructor calls Monitor::Exit. Creating and deleting the guard around each read/write of bContinue makes the shared flag safe. C# has a lock keyword; C++/CLI does not, hence the helper class.
  • A deadlock is mutual waiting: the traffic-jam figure below shows the classic four-way standoff. Here it could happen if the worker is suspended while holding the flag's lock. Detection and recovery are deferred to Chapter 8.

Thread safety and wait handles

  • In .NET, static members are thread-safe; instance members are not. Two threads enumerating the same List<int> each get their own enumerator, which is safe as long as nobody mutates the list.
  • initonly gives safe concurrent reads, illustrated by SafeValue::iValue being read by two Tasks.
  • Locks cost waiting time and can deadlock, so design the data sharing first. ManualResetEventSlim replaces the shared flag and polling: the worker calls Reset() then Wait(); the UI calls Set() when the user answers. With roughly 40 ns overhead it is ideal for short waits inside one process; for long waits it behaves like a normal ManualResetEvent.

Event-based asynchronous pattern and BackgroundWorker

  • EAP means the class creates and manages the worker for you: call WebClient::DownloadDataAsync, subscribe DownloadDataCompleted, and the handler runs on completion with the result in e->Result.
  • The factorial example imitates this with a static EndTaskEvent instead of a window message — it therefore also works in a console program with no message queue. The price: every UI change inside the event handler must still be marshalled with BeginInvoke because the event fires on the worker thread.
  • BackgroundWorker (in System::ComponentModel) is the general-purpose EAP implementation. Set WorkerReportsProgress, wire DoWork, ProgressChanged and RunWorkerCompleted, then call RunWorkerAsync. ReportProgress(i) raises the progress event and the completion event carries e->Result — no manual delegates for controls.
  • Unlike the sealed Thread, BackgroundWorker can be subclassed; override OnDoWork to carry extra state (the book's example is a weather prediction with many fields).

Interrupting, aborting and cancelling safely

  • Thread::Interrupt only throws ThreadInterruptedException when the target blocks (or the next time it blocks) — it may appear to do nothing on a running thread.
  • Thread::Abort works on non-blocked threads and throws ThreadAbortException, but both forced methods are unsafe: unmanaged code continues until the next managed statement, and you cannot fully predict the state you leave behind.
  • The recommended path is cooperative cancellation: set WorkerSupportsCancellation = true, call CancelAsync() from the closing form, and check worker->CancellationPending inside the loop to return cleanly.
  • Task::ContinueWith attaches a follow-up task that uses the first task's result. WaitAll and WaitAny are the managed cousins of the native wait APIs.

Non-blocking synchronization — fences and volatile

  • The compiler and CLR may reorder statements or cache reads/writes for optimisation. In the TestClass example, GetMethod can observe bState == true but still print iValue == 0.
  • Thread::MemoryBarrier() creates a full fence (~10 ns) around the flag: writes before it cannot move after, reads after it cannot move before.
  • Declaring the flag volatile gives cheaper half fences: an acquire fence on each read and a release fence on each write, leaving more room for optimisation.

Wait/Pulse and the Barrier class

  • Monitor::Wait and Monitor::Pulse/PulseAll suspend and wake a thread without spinning, but must be called while holding a lock. The worker waits on syncHandle, the UI thread pulses it after the user answers, and execution continues. A pulse costs about 100 ns versus ~400 ns to set an event handle.
  • A Barrier coordinates phases: create it with N participants, each calls SignalAndWait(), the counter drops, and only when it reaches zero are all tasks released. AddParticipant, RemoveParticipant, ParticipantCount and ParticipantRemaining manage the group.
  • The post-phase delegate passed to the constructor runs while all tasks are still paused — perfect for drawing the finished graph in CLRBarrier, where Parallel::Invoke runs two halves of one symmetric plot and EndTask paints the bitmap.
Chapter's closing advice: all these constructs are useful, but no single one fits every task. Understand the trade-offs, then choose deliberately before coding.

44 Chapter 7: detailed summary

Correctness versus liveness

  • Correctness problems make a program produce wrong results. They are hard to catch because each thread follows a different path; a program may return correct answers many times before one bad interleaving appears.
  • Liveness problems make a program stop producing results — it hangs or becomes unresponsive rather than crashing. Deadlock is the chapter's main example.
  • Poorly designed parallel code can be slower than sequential code: rescheduling threads, fetching memory blocks, signalling objects and maintaining protection all cost CPU time.
  • Chapter 6 said "choose the right synchronisation object". Chapter 7 adds "choose the right design" — the object alone cannot repair a wrong execution flow.

Data races and inconsistent synchronisation

  • A data race occurs when several threads read and write a shared object without a defined order. The chapter's iValue = 5 example copies it into two thread-local variables at different times; without mutual exclusion the final value is unpredictable.
  • Protection must be consistent. The CLock wrapper calls CreateMutex with a name and waits in its constructor, then releases and closes in the destructor. If funcA uses _tmp_lock_01_ and funcB uses _tmp_lock_02_, they protect nothing relative to each other — both increment the same iValue concurrently.
  • Even read-only sharing can be dangerous when combined with writes elsewhere; classify each shared object before deciding what to protect.

Composite actions — lock the whole critical region

  • Removing the head of a singly linked list needs two statements: node == NULL then next = node->next. The first incorrect version protects only the assignment.
  • The interleaving figure shows why that fails: thread A checks the list is non-empty, is suspended, thread B checks the same thing, A removes the node, and B then dereferences a node that no longer exists — "APP CRASH".
  • The correct version takes the lock before the NULL check and releases it after the assignment. Fewer protected statements mean more concurrency, but you must include the entire logically atomic sequence.
  • Group critical points into small, heavily protected portions, then examine every use case before declaring the flow safe.

Deadlock in the bank transfer

  • CBankAccount::Transfer(a, b, amount) locks account A, then account B, adjusts both balances, and releases both locks. It looks correct.
  • With two opposite transfers — A→B and B→A — thread A acquires lock_1 on X and thread B acquires lock_2 on Y. Each then waits for the lock the other holds. The second timing figure shows both threads "WAIT FOREVER".
  • The event may be rare, but a concurrent design must rule it out, not merely hope it never happens. A common fix is to acquire locks in a consistent global order.

Design before code — Schwefel's function

  • The example computes Schwefel's function over an array of up to 100,000 random alleles in [-65.536, 65.536]: square the inner sum for each position, accumulate score, and track sum, minimum and best value.
  • CSchwefel is deliberately designed for extension: Evaluate and the destructor are virtual, one void* parameter is reserved for thread arguments, the copy constructor and assignment operator are disabled (a shallow copy would leave two objects pointing at one allele array), and ObjectName() is overridden by each derived class for the console output.
  • Initialize fills the array and computes the initial sum/min; Elapsed formats timings using a custom SYSTEMTIME subtraction operator built on SystemTimeToFileTime and FileTimeToSystemTime.
  • The entry point simply constructs CSchwefel(100000), calls Evaluate() and prints Elapsed(). Strong sequential code first; parallelism is added only afterwards.

From sequential to multi-threaded

  • CSchwefelMT derives from CSchwefel and overrides only Evaluate. It splits the array into ThreadNumber chunks, passes a ThreadParams structure to each CreateThread, waits with WaitForMultipleObjects, then closes handles.
  • The naive StartAddress updates Sum(), Min(), Score() and Best() directly from every thread. The third figure shows the harm: two CPUs both load dSum = 42.56 from address 4004, add different alleles, and write back one value — the other addition is lost.
  • The corrected version reads the shared values once under a mutex into thread-local dSum/dMin/dScore/dBest, performs the whole loop without locks, then takes the mutex again to merge the results. Protected boundaries, parallel middle — "safe and clean".
  • Putting the mutex inside the loop would serialise nearly all the work and defeat the purpose of parallelism.

OpenMP and measuring improvement

  • CSchwefelP uses the compiler's OpenMP support: #pragma omp parallel firstprivate(min) firstprivate(best) gives each thread its own copies of the extrema; #pragma omp for reduction(+: sum) reduction(+: score) nowait splits the loop and merges the sums safely; #pragma omp critical serialises the final comparison of min/best.
  • firstprivate initialises each private copy from the value before the region; reduction combines private results at the end under mutual exclusion; nowait removes the implicit barrier at the loop's end.
  • Improvement is I = T(S) / T(P). I < 1 is slowdown, I < P sublinear, I ~ P linear, and I > P superlinear (rare, sometimes possible when intermediate results are shared).
  • On an Intel i7-3820 with 8 logical cores: sequential 4057 ms, 8-thread CSchwefelMT 955 ms → I = 4.248; OpenMP 959 ms → I = 4.231. Both are sublinear — the normal result when synchronisation and communication exist.
  • A slowdown can also mean the code was poorly parallelised, had too many protection points, or the target hardware has fewer cores than the test machine. Measure before and after, on the hardware that matters.
Chapter's closing advice: plan from design to code in steps, decide whether parallelism actually helps, and let practice confirm the theory.

51 Chapter 8: detailed summary

Why a manager object?

  • Complex programs need mechanisms above individual threads. The book points to the Windows Dispatcher (scheduling and synchronisation) and the Virtual Memory manager as examples of one root object responsible for managing many tasks.
  • Such a manager creates and destroys tasks, checks that resources are available, grants exclusive access, and ensures no two tasks perform invalid or unsynchronised operations.
  • With parallelism comes a thread hierarchy: some threads are more important and must supervise others. Design that hierarchy before writing the workers.

The basic thread pool

  • A pool is a list of worker threads available to execute tasks. It helps when an application would otherwise spawn a large number of short-lived threads — creation and destruction overhead dominates the actual work.
  • CThread wraps a start address, handle, thread ID and exit code. Its destructor terminates a still-running thread; Start calls CreateThread, StillAlive compares GetExitCodeThread with STILL_ACTIVE.
  • CThreadPool stores CList<CThread> and a maximum count (logical processors by default). RequestThread creates a new worker while below the cap; otherwise it polls every 100 ms until a worker finishes, removes it and inserts a replacement. WaitAll uses WaitForMultipleObjects with bWaitAll = TRUE.
  • The demo program creates twelve CBankAccount objects with random balances and submits five random transfers. CLock again guards two named mutexes, and the transfer returns 1 on success or 0 when funds are insufficient.
  • Limitation: a deadlock can still happen if two opposite transfers overlap exactly. Polling alone cannot detect it — which motivates the smarter dispatcher.

Custom dispatcher: worker and context thread

  • Rather than polling the list, completion now uses message passing: the first worker to finish posts MSG_ENDTASK to the dispatcher, which blocks in GetMessage and wakes only when a task is done.
  • Each pool item is a worker thread created with CREATE_SUSPENDED. Its StartAddress creates a second context thread that runs the user function, then waits at most MAX_WAIT_TIME (120 s, adjustable with SetMaxWaitTime), closes the context handle and posts the completion message carrying the worker ID.
  • If the context thread terminates or hangs, the worker notices through its exit status or timeout and can notify the dispatcher. This doubles the thread count per task but preserves the pool cap and gives fine-grained control.
  • CBankAccount::Transfer gains a deliberate Sleep(100) at the start so that opposite transfers reliably overlap and create the deadlock the problem solver must handle.

The ProblemSolver and Wait Chain Traversal

  • CThreadPool now includes Wct.h and links Advapi32.lib. It owns a hProblemSolver thread, a manual-reset hEvent for shutdown, the worker list and the cap.
  • The monitoring thread must be outside the pool — if it were a pool worker it could be blocked along with the pool. Each loop waits 10 ms on the exit event, then inspects every worker with StillAlive.
  • For each live worker it opens a Wait Chain Traversal session with OpenThreadWaitChainSession and calls GetThreadWaitChain on the context thread. A wait chain alternates threads and synchronisation objects; when the nodes form a cycle, the API sets IsCycle to TRUE.
  • On a detected cycle the solver calls TerminateThread on the context handle, prints "Error! Deadlock found! Thread: [id] terminated!", closes the WCT session, sleeps one second and keeps watching. The screenshot shows two accounts repeatedly transferring until a cycle is found and broken.
  • The destructor signals the event, waits up to MAX_WAIT_TIME for a clean exit, forcibly terminates the monitor only if needed, then closes handles, removes workers and clears the message queue.
  • The book names this scenario the Banker's algorithm (Edsger Dijkstra) and notes that the same pool-plus-solver pattern generalises to other deadlock-prone work.

Remote threading

  • Sometimes you must change behaviour in compiled code you cannot edit. A remote thread runs in another process's address space. Windows offers CreateRemoteThread, SetWindowsHookEx and the undocumented NtCreateThreadEx; the chapter uses the first.
  • A function address in your own process is useless in the target, so the thread's start address must be a system function: LoadLibraryA. Its argument — the absolute DLL path — is written into the target with VirtualAllocEx and WriteProcessMemory. The remote thread loads the DLL, and DllMain(DLL_PROCESS_ATTACH) runs your code in that process.
  • common.h shares the file-mapping and event names between the EXE and DLL. In the DLL, OpenFileMapping obtains a structure where it writes hInstance — the DLL handle the parent needs later for FreeLibrary.
  • The example changes the main-window title of calc.exe. EnumWindows visits top-level windows, GetWindowThreadProcessId matches the owning process, and IsMainWindow checks no owner plus IsWindowVisible; then SetWindowText changes the title and SetEvent tells the parent the job is done.
  • The parent starts calc.exe with CreateProcess, waits 500 ms for initialisation, calls RemoteLoadLibrary, waits on the event, maps the shared view, calls RemoteFreeLibrary with the reported handle, then closes handles. For an existing target, OpenProcess must request PROCESS_ALL_ACCESS or CreateRemoteThread will fail.
Book's closing advice: concurrency rests on operating systems, compilers, OOP, execution and runtime knowledge. Get the design right first, then practise — a lot.
